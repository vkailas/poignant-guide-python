    Eval, The Littlest Metaprogrammer

    The following experiments belong in a scratch Python session. Start a fresh session for the saved game classes so experimental class redefinitions do not affect them.

    We've spent some time building up objects using object-oriented programming. Classes have attributes and behavior, child classes inherit from their parents, and properties give us a clean interface to an object's attributes.

    But Python has another trick up its sleeve. Metaprogramming is writing code which writes code. But the program doesn't jump onto your screen and wrench the keyboard from your hands. It's much more civilized.

    Python lets you execute code while your program is running using eval().

    The eval() function takes a string and asks Python to evaluate it as an expression.

    For example: 

    eval("1 + 2")
# 3

    A string becomes code. Python reads it, understands it, and gives you the result. This is where things start getting a little interesting.

    You can even tuck the name of an attribute into a string: 

    class Dragon():
    _life = 1340       # tough scales
dragon = Dragon()
trait = "life"
eval(f"dragon._{trait}")
# 1340

    I totally understand if you've come to this point and your eyes are spinning in their sockets and your knees have locked up. Just rub some tiger balm on your joints while I talk about eval.

    For our purposes, the interesting part isn't that eval() can do simple math. It's that Python can take a description of code and turn that description into something executable. Python is taking our little strings and turning them into instructions. It's like handing a note to a very literal laboratory assistant:

    "Please examine the dragon's life."

    Your assistant squints at the note, turns it into Python code, and heads into the laboratory. This is a tiny taste of metaprogramming: writing code that works with code. But don't get too excited about handing eval() every mysterious scrap of paper you find. If the string comes from somewhere you don't trust, Python will happily evaluate whatever code is inside it. In other words, eval() is a powerful little creature. Keep it on a short leash.

    The interactive interpreter displays the result of an expression when that result is not None. Assignments and other statements do not automatically display a result. It is a little conversation between you and Python, but not every line gets an answer.

    You could write your own Python shell prompt very easily:

    print(">> ", end="")
result = eval(input())
print("=>", repr(result))

    This is a one-shot expression evaluator, not a complete REPL: there is no loop, and eval() cannot execute statements such as assignments or for loops. Use it only with input you wrote and trust; it is not a sandbox. For an actual interactive session, use Python’s built-in shell. How do you like that? Two of your recently learned concepts have come together in a most flavorful way. The eval() takes the typed code and runs it. The response from eval() is then passed to repr(), which gives us the useful representation of the resulting object.

    The interactive interpreter intends to spit out useful representation for programmers, and repr() does just that. When you're building a little interactive prompt like this, repr() is exactly what you want.

    Suppose we have our Dragon and want to print a list of our dragon's traits:

    class Dragon():
    _life = 1340       # tough scales
    _strength = 451    # bristling veins
    _charisma = 1020   # toothy smile
    _weapon = 939      # fire breath

dragon = Dragon()  # an instance of this newly defined class

    traits = ["life", "strength", "charisma", "weapon"]

    We could use eval(): 

    for trait in traits:
    print(eval(f"dragon._{trait}")) #not recommended

    Python gives you metaprogramming powers, but that doesn't mean you should use them for everything. Most of the time, we do write out classes and methods normally for readability. For example, using eval() like this is generally not recommended. If untrusted text reaches eval(), it can execute arbitrary code. Instead, we could use getattr() when you need an attribute whose name is stored in a string. getattr() performs attribute lookup rather than parsing Python source. It does not validate attribute names for you: use an explicit allowlist if callers must be restricted to certain attributes. Properties and custom lookup hooks can still run code during attribute access.

    Instead of using eval to print all traits, we could have used getattr. 

    for trait in traits:
    print(getattr(dragon, f"_{trait}"))

    Now that you've seen how Python can read an attribute whose name is stored in a string, it's time to peek at an even stranger trick. We could create a new Creature class where each property is created dynamically:

    class Creature:
    _magic = 10
def magic(self): return self._magic
setattr(Creature, "magic", property(magic))

    That's a rather astonishing line that creates a new property to access a class variable on the fly.

    The above code is the equivalent to creating a getter property like this: 

    class Creature:
    _magic = 10
    @property
    def magic(self): # getter
        return self._magic

    But it can be done at run-time, creating new properties for a dragon out of thin air.

    How does it work? We use setattr(object, name, value). The object is Creature class, the name is "magic", and the value is a property(magic). When someone asks a creature for its magic, this new setattr code tells Python to reach inside the object and give back _magic.

    As we have seen before this is called monkey patching as we are modifying a class at runtime, but it is also metaprogramming as we are writing code that modifies a program's structure at runtime.

    Let's go ahead and use the new property to access the creature's _magic class variable without having to use the _:

    >>> class Creature:
...     _magic = 10
...     _hair = 0   # hairless creature
...
>>> def magic(self):
...     return self._magic  # getter
...
>>> setattr(Creature, "magic", property(magic))
>>> creature = Creature()
>>> creature.magic
10
>>> def hair(self):
...     return self._hair  # getter
...
>>> setattr(Creature, "hair", property(hair))
>>> creature = Creature()
>>> creature.hair
0

    Python is constructing part of a class for us (getter property methods) while the program is running. But why would we want to do this?

    Imagine you have dozens of creature traits that you want to make into property attributes:

    _life
_strength
_charisma
_weapon
_speed
_armor

    Writing the same @property over and over would become rather tedious. If all those properties follow the same pattern, Python can create them for us using a generic lambda function to replace the property function definitions, getattr to lookup the correct attribute, and a for loop to loop over the attributes and set each on:

    def make_getter(name):
    return lambda self: getattr(self, f"_{name}")

for trait in ["life", "hair", "strength", "charisma", "weapon", "speed", "armor"]:
    setattr(Creature, trait, property(make_getter(trait)))

    def magic(self): # getter
    return self._magic

setattr(Creature, "magic", property(magic))

    Now one small piece of code creates the property descriptors. Each corresponding backing attribute must still exist before you read a property; otherwise it raises AttributeError.

    Each call to make_getter(name) creates a separate enclosing scope, so each returned lambda closes over its own name.

    That's when metaprogramming starts earning its keep. We're no longer using a complicated trick to replace one simple property. We're using Python to handle a whole family of repetitive definitions.

    The laboratory doors are beginning to creak open. And somewhere inside, something is learning how to program itself.

    And with the case of our little spell to create a property on the fly: 

    class Creature:
    _magic = 10
def magic(self):return self._magic
setattr(Creature, "magic", property(magic))

    The explicit version that creates a property is waaay easier to read:

    class Creature:
    _magic = 10

    @property
    def magic(self): # getter
        return self._magic

    Anyone opening the file can immediately see what magic does (creates a getter property). But with setattr() version, they have to stop, squint at the machinery, and mentally unpack what the program is doing.

    Remember, the Pythonic approach is generally to use plain code when it does the job. Reach for dynamic techniques ONLY when they actually make a problem simpler. Don't summon a Python wizard when a perfectly good carpenter is standing right there with a hammer. However, when you have a whole menagerie of creature traits, suddenly that wizard starts looking rather useful.

    Store these little metaprogramming tricks away as we'll need to use them on our rabbit's path to glory.

    Creature Code

    Object-oriented programming is a way of organizing code around objects. Let's say it's more like a little orange pill you won at the circus. When you suck on it, the coating wears away and behind your teeth hatches a massive, floppy sponge brontosaurus. He slides down your tongue and leaps free, frolicking over the pastures, yelping, "Papa!" And from then on, whenever he freaks out and attacks a van, well, that van is sparkling clean afterwards.

    Now, let's say someone else puts their little orange pill under the faucet. Not on their tongue, under the faucet. And this triggers a different cataclysm, which births a set of wailing sponge sextuplets. Umbilical cords and everything. Still very handy for cleaning the van. But an altogether different kind of chamois. And, one day, these six will stir Papa to tears when they perform the violin concerto of their lives.

    That's rather like what we're doing with classes. We put some common behavior and attributes into a class, and then use that class as a blueprint for creating objects.

    The Creature class is our little orange pill. It contains the machinery that all our creatures can use.

    Now, with a lateral slice across the diaphragm, we expose the innards of Creature.

    class Creature:
    def __init__(self, slogan=""):
        self.slogan = slogan
        self._life = type(self)._life
        self._strength = type(self)._strength
        self._charisma = type(self)._charisma
        self._weapon = type(self)._weapon

    @property
    def life(self):
        return self._life

    @property
    def strength(self):
        return self._strength

    @property
    def charisma(self):
        return self._charisma

    @property
    def weapon(self):
        return self._weapon

    @property
    def name(self):
        return self.__class__.__name__

    def __repr__(self):
        return f"<{self.name}(life={self.life})>"

    The line below gives each creature instance its own starting life:

    self._life = type(self)._life

    This code initializes an instance variable from a class default. We read the starting life from the creature’s class (Rabbit, Dragon, etc.) and store it on the individual instance. During combat, changes to self._life affect that creature, leaving the class default unchanged.

    Python distinguishes class attributes from instance attributes. For these underscore-prefixed data attributes, an instance’s own value takes precedence over the class default with the same name.

    Now, focus on the four properties being set up in Creature. These are the little windows through which we can inspect the creature's innards. The values themselves are class-level defaults (class variables) supplied by each creature subclass.

    A Dragon is one of the creatures produced from that machinery. We can create a dragon by giving it its default values:

    class Dragon(Creature):
    _life = 1340       # tough scales
    _strength = 451    # bristling veins
    _charisma = 1020   # toothy smile
    _weapon = 939      # fire breath

    Our Dragon class supplies the default values such as _life, but the instance keeps track of its own changing _life.

    We do the same for the other attributes _strength, _charisma, and _weapon, tying them to the instance.

    So when Python encounters:

    >>> my_dragon = Dragon()
>>> my_dragon.life
1340
>>> my_dragon.strength
451

    The inherited getter properties spring into action and return the corresponding instance values from my_dragon.

    It's almost as if Python sneaks into the laboratory after hours, rummages through a drawer of spare monster parts, bolts everything together, transplants a spiny green heart, and gives the creature a healthy jolt of electricity.

    POWER UP! POWER UP!

    The resulting dragon is remarkably compact:

    class Dragon(Creature):
    _life = 1340       # tough scales
    _strength = 451    # bristling veins
    _charisma = 1020   # toothy smile
    _weapon = 939      # fire breath

    Yet it already knows how to expose its attributes via the properties and methods from Creature:

    >>> dragon = Dragon()
>>> dragon
<Dragon(life=1340)>

    But how does the Dragon know what it is when the __repr__ method is called from inside Creature??

    This __repr__() uses runtime introspection for an object to find out what type of Creature it is. It reads the instance’s class name to provide a helpful representation e.g. <Dragon(life=1340)>. Proper representation isn’t usually a part of dealing with a monster. It’s something Dwemthy adds as a courtesy to our players at the bottom of the Creature class.

    Many call him twisted, many call him austere, but we’d all be ignorant to go without admiring the footwork Dwemthy puts in for us. 

    >>> print(dragon.life)
1340

    And notice that we access dragon.life, not dragon._life. Again the underscore attributes are the creature's internal machinery and are a polite way of saying to users, "This is my internal machinery. Please don't poke it directly."

    The properties defined by Creature provide the clean public interface that we can use with the Dragon class:

    >>> print(dragon.strength)
451
>>> print(dragon.charisma)
1020
>>> print(dragon.weapon)
939

    The dragon never defines those properties and methods itself. They are inherited from Creature just as a baby dragon inherits his mother's eyes.

    This is one of the pleasures of object-oriented programming. You teach a parent class a few tricks, and all of its descendants inherit them. One lesson, many monsters.

    Our laboratory is beginning to look quite respectable.

    Enough Belittling Instruction and Sly Juxtaposition—Where Is Dwemthy’s Array??

    We've now given our creatures attributes, inherited those attributes from a parent class, and taken our first peek behind the curtain at code that can write other code.

    Tread carefully—here comes the other half of DWEMTHY’S ARRAY!!

    Replace the preliminary Creature definition and save this completed version in dwemthy.py. It includes the properties from before plus the battle methods and DwemthysArray.

    dwemthy.py
    import random

class Creature:
    def __init__(self, slogan=""):
        self.slogan = slogan
        self._life = type(self)._life
        self._strength = type(self)._strength
        self._charisma = type(self)._charisma
        self._weapon = type(self)._weapon

    @property
    def life(self):
        return self._life

    @property
    def strength(self):
        return self._strength

    @property
    def charisma(self):
        return self._charisma

    @property
    def weapon(self):
        return self._weapon

    @property
    def name(self):
        return self.__class__.__name__

    def __repr__(self):
        return f"<{self.name}(life={self.life})>"

    # -- new methods --- 

    def __call__(self):
        if self.slogan:
            print(self.slogan)

    # This method applies a hit taken during a fight.
    def hit(self, damage):
        if self.life <= 0:
            return
        power_up = random.randint(0, self.charisma)

        if power_up % 9 == 7: 
            self._life += power_up // 4
            print(f"[{self.name} magick restores {power_up // 4} life points!]")

        self._life -= damage

        if self._life <= 0:
            print(f"[{self.name} has died.]")

    # This method takes one turn in a fight.
    def fight(self, enemy, weapon):
        if self.life <= 0:
            print(f"[{self.name} is too dead to fight!]")
            return

        # Attack the opponent
        your_hit = random.randrange(self.strength + weapon)

        print(f"[You hit with {your_hit} points of damage!]")
        enemy.hit(your_hit)

        # Retaliation
        print(enemy)

        if enemy.life > 0:
            enemy_hit = random.randrange(enemy.strength + enemy.weapon)

            print(f"[Your enemy hit with {enemy_hit} points of damage!]")
            self.hit(enemy_hit)

    Method Missing: Aside to understand Closures and __getattr__

    Calling a Ghost named Simon

    Don’t you hate it when you yell “Deirdre!” and like ten people answer? That never happens in Python. If you call the deirdre method, Python looks for an attribute named deirdre and, if it finds one, that’s the one you get. You can’t have two methods with the same name in a class. If you add a second deirdre method, the first one disappears.

    You can, however, have an object which answers to names that don’t actually exist, using metaprogramming.

    class CallSomeName:
    def __getattr__(self, name):
        def dynamic_method(*args):
            print(f"You're calling `{name}` and you say:")
            for say in args:
                print("  " + str(say))
            print("But no one is there yet. :(")
        return dynamic_method

    def deirdre(self, *args):
        print("Deirdre is right here! She heard you say:")
        for say in args:
            print("  " + str(say))
        print("And she loves every second of it.")
        print("(I think she thinks you're poetic.)")

    Well, deirdre has a method already, so Python finds it normally:

    >>> name_caller = CallSomeName()
>>> name_caller.deirdre("Howdy!")
Deirdre is right here! She heard you say:
  Howdy!
And she loves every second of it.
(I think she thinks you're poetic.)

    But what if you call simon?

    >>> name_caller.simon("Hello?", "Hello? Simon?")
You're calling `simon` and you say:
  Hello?
  Hello? Simon?
But no one is there yet. :(

    Here is what happens:

    • Python cannot find simon, so it calls __getattr__ with "simon" as name.
    • __getattr__ defines dynamic_method and returns it without running it.
    • Python calls that returned function with arguments "Hello?" and "Hello? Simon?".
    • The function prints the missing name and the supplied messages. The *args parameter collects those messages into a tuple, loops over those, and prints them too.

    But how does dynamic_method remember "simon" after __getattr__ has returned dynamic_method and dynamic_method has entirely new arguments being passed in "Hello?" and "Hello? Simon?" e.g. dynamic_method("Hello?", "Hello? Simon?").

    Imagine you hire a little assistant, give them a task, and send them off into the world. Before they leave, you whisper a few important details in their ear: “When you see Alice, give her the blue envelope.” The assistant remembers. Even after you have left the room, they still have that information tucked away.

    A closure can do something similar. A closure is a function that remembers variables from the place where it was created. This is useful when we want to create a function with some information already attached to it, so the function can use that information later.

    Let's take a quick example to see how it works: 

    def make_tax_calculator(tax_rate):
    # This outer function 'remembers' the tax_rate
    def calculate_total(price):
        # The inner function calculates tax and adds it to the price
        return price + (price * tax_rate)
    return calculate_total

# Create a specific calculator for a Wixl's super high 17% sales tax
wixl_tax = make_tax_calculator(0.17)
# Create a specific calculator for a Endertomb's lean 5% sales tax
endertomb_tax = make_tax_calculator(0.05)
print(wixl_tax(100))      # 117.0
print(endertomb_tax(100)) # 105.0

    Each of the factory methods, wixl_tax and endertomb_tax, remembers its own specific tax_rate.

    Our __getattr__ works like this little function factory, too. Each missing name lookup creates a function that remembers its own name:

    simon_caller = name_caller.simon("Hello?")
blix_caller = name_caller.blix("Hello?")
fox_caller = name_caller.fox_small("Hello?")

    The function created for simon remembers "simon"; the one created for blix remembers "blix"; and the one created for fox_small remembers "fox_small". The messages arrive when those functions are called and are stored as name so we have a record of who the caller was.

    That's the useful trick behind a closure: a function can carry a little piece of its creation history around with it. And __getattr__ acts like an answering machine that intercepts your method calls.

    It's a great trick but __getattr__ only works when the normal lookup fails. The deirdre method doesn’t need an answering machine. She’s already there.

    Closures bind variables

    Remember: A closure is a function that remembers variables from its enclosing scope.

    Look at that definition more closely: a closure remembers the variables, not just the values they had when the function was created. When the inner function runs, it can access the variables' current values.

    For example:

    title = "Mrs."

    def greet():

    return greet

    The Dynamic Monster Mash: Delegation, Closure, and Duck Typing

    Delegation routes a request or tasks to an inner helper object. A closure retains access to information from an enclosing function. Our array combines them: it delegates a call for a missing attributes to the first monster in the list (kind of like call forwarding) and wraps methods so it can do clean up after the call.

    Here is the same complete class included in dwemthy.py. Do not append a second copy:

    class DwemthysArray(list):
    def __getattr__(self, name):
        if not self: # empty list
            if name == "life":
                return 0
            raise AttributeError(name)
        monster = self[0]
        attr = getattr(monster, name)
        if not callable(attr):
            return attr

        def dynamic_access(*args, **kwargs):
            # call the method
            result = attr(*args, **kwargs) 
            assert self and self[0] is monster, "The attacking monster is gone!"

            # clean up
            if monster.life <= 0:
                self.pop(0)
                if self:
                    print(f"[Get ready. A wild {self[0].name} has emerged.]")
                else:
                    print("[Whoa. You decimated Dwemthy’s Array!]")

            return result
        return dynamic_access

    For attributes like dwary.life, the array returns the first monster’s life value directly.

    For methods like dwary.hit, it returns a closure that remembers the bound method attr, the selected monster, and the array self. Calling dwary.hit(...) executes that method and then removes the monster if it died. *args and **kwargs forward both positional and keyword arguments.

    Each time rabbit attacks, its fight() method calls enemy.hit(...), and the array forwards the hit to the current first monster.

    Now why do we need a closure here? Checking whether the monster died during attribute lookup (inside of __getattr__) would be too early: the attack has not happened yet. The closure first calls the monster’s method (like monster.hit(...)), then checks its life and removes dead monsters. The closure gives us a straightforward place to handle cleanup and prevent zombie monsters from overstaying their welcome.

    Do you see the assert statement in the dynamic_access?

    In Python, the assert keyword acts as an internal sanity check for your code to ensure a condition is true. 

    assert self and self[0] is monster, "The attacking monster is gone!"

    The assert statement here checks "Is the list not empty and is the monster we attacked still first in the list?” Assert statements are not absolutely necessary code but defensive coding and help catching internal bugs that you expect should never happen if your logic is sound.

    A good programmer uses assert to keep to test internal code assumptions, document expected states, and catch logical bugs early during development. Use them liberaly.

    You use an assert statement like so: assert condition, optional_error_message.

    Notice that self.pop(0) calls a normal list method, which simply removes an element at a certain index! Python finds pop() inherited from the superclass list, so it does not need to call __getattr__.

    So the result of our clever DwemthysArray class, the rabbit can attack a list (well a customer version of list)! The list simply asks the first monster, “Do you know what method this is?” Finally, the list returns a dynamic_access closure, which calls the first monster’s method (like monster.hit(...)) and handles cleanup afterward (cleaning out dead monsters so they don't stink up the place).

    Duck Typing: Our Array Behaves Like an Opponent

    Creature has no knowledge of DwemthysArray or that it is a list. Creature simple asks an opponent for life, strength, weapon, and calls its hit() method. This is duck typing: using an object’s expected interface rather than checking its particular class.

    The DwemthysArray does not store a life value. When asked for life, it simply returns the first monster’s life. If no monsters remain, then it returns 0.

    An empty list therefore can behave like a defeated opponent! We don't want to beat a dead list.

    After a monster dies, DwemthysArray removes it immediately from the front of the list with pop(0). If another monster remains, the next enemy.life lookup now sees the new lead monster, which can retaliate during the same turn.

    After the final monster is removed, enemy.life returns 0. The conditionenemy.life > 0 is false, so there is no need to fight. The rabbit puts his lettuce down. Victory is ours!

    Import the various classes, create our rabbit, define the foes, and put them into a DwemthysArray. Finally the rabbit gets to start his quest: 

    rabbit % dwary

    Just remember to save a bomb for the finale!

    Delegation, closures, and duck typing allow our bold rabbit to fight an entire list of monsters rabbit % dwary and fulfill his destiny without having to fight zombies.

    5. I'm Out

    One day, back around the time I met Bigelow (that dog who walked off with the balloons), I came back to my apartment hauling some board games I’d bought at a garage sale. And Quil was on my porch. Which stunned me since she’d been in San Antonio for like three years. She was sleeping in a sleeping bag on my porch.

    She had run out of money to go to art school, so she stayed at my place for five months or so.

    I found this used bunkbed for our place. At night we’d sit in our beds and read each other stories from our notebooks. I was writing a book about a kid who’s a detective and he’s trying to figure out who killed this kid on his tennis team and all these animals end up helping him figure it out. She was writing a book about this kid who puts an ad in the classifieds to get other kids to join his made-up cult and they end up building a rocket ship. But during most of her book these kids are lost in the woods and pretty directionless, which I got a kick out of hearing each night.

    Yeah, each night it was poetry or stories or ideas for tricking our neighbors. Our neighbor Justin was a big fan of Warhammer and he had all these real swords and tunics. We decided to make suits of armor out of tin foil and go attack his apartment. We started ransacking his apartment and he loved it. So he made his own suit of armor out of tin foil and we all went to a professional glamour studio and had a quality group shot taken.

    I’m not saying my life is any better than yours. I just miss my sister. Life isn’t like that now. We’re dissolved or something.

    I don’t know. I’m confused. Is this growing up? Watching all your feathers come off? And even though some of those feathers were the most lovely things?

    I’m having a hard time telling who stopped it all up. Who stopped loving who? Did I stop caring? Maybe I only saw her in two-dimensions and I didn’t care to look at the other angles. I only saw planes. Then she shimmied up the z-axis when I wasn’t looking and I never did the homework to trace the coordinates. A limb on a geometrical tree and I am insisting on circles.

    Blix was right. I’m in no shape to write this book. Goodbye until I can shake this.
